# Claude Code · Codex · Song 공동 작업큐

2026-10-18 도입. 목적은 다음 일을 미리 준비하고, 파일·실행 자원을 겹치지 않게 점유하는 것이다.
기존 [협업 규약](collab-protocol.md)과 [실행 절차](workflow.md)를 보완하며 권한·연구·운영 게이트는 바꾸지 않는다. 새 세션은 [공통 시작 프롬프트](kickoff.md)를 사용할 수 있다.

## 한곳에서 계획하고 선점하기

- [공동 작업큐 #37](https://github.com/SongRoute/pitcheezy/issues/37): 작업 계획·소유권·인계는 **추가 전용 댓글**로 기록한다. 기존 댓글을 고쳐 이력을 지우지 않는다.
- [상황판 #35](https://github.com/SongRoute/pitcheezy/issues/35): 목표·진행 중·막힘의 요약과 작업큐 링크만 유지한다.
- 작업큐 본문이 오래됐으면 소유권은 유효한 댓글 이력이 우선한다. 계약·결과의 정본은 해당 고정 커밋·등록·증거이며 댓글이 이를 대체하지 않는다.
- GitHub 계정이 같아도 `actor=ClaudeCode|Codex|Song`, `session=<고유 세션 ID>`를 반드시 적는다. 대리 기록은 `reported_by`를 따로 적고 당사자 수락과 구분한다.
- 도입 당시 공통 문서·작업큐 본문·#35 요약 지정 편집자는 **COORD-00의 Codex 세션**이었다. 현재 편집자는 최신 큐의 CLAIM·DONE·RELEASE 등 유효 댓글 이력으로 확인한다. 지정 편집자 외 참여자는 댓글만 쓰며, 편집자 교체도 RELEASE → 새 CLAIM으로 기록한다.
- 하위 에이전트는 PM 세션이 대표 등록하되 실제 작성자와 검토자를 구분한다. 같은 checkout의 git index를 동시에 조작하지 않는다.
- 댓글 선점은 참여자가 지키는 협업 절차이며 OS/원자적 lock이 아니다. 실제 자원의 기존 lock은 별도로 유지한다.

## 상태와 댓글 동작

| 상태/동작 | 의미 |
|---|---|
| `PLAN` / `READY` | 완료 조건·선행 입력·범위를 준비한 제안. 담당 추천은 수락이나 착수가 아니다. |
| `RESERVED` | 기존 소유권 또는 당사자가 수락한 다음 작업 예약. 아직 실행 중이라는 뜻은 아니다. |
| `CLAIM` / `ACTIVE` | 아래 선점 절차를 통과한 실제 착수. 작성·실행 범위를 정확히 고정한다. |
| `REVIEW` | 고정 커밋과 증거를 제출하거나 독립 검토 결과를 추가한다. 작성 소유권은 유지된다. |
| `BLOCKED` | 막힌 이유·필요 입력·다음 확인 시점을 남긴다. 소유권을 자동 반환하지 않는다. |
| `RELEASE` | 편집·실행을 멈추고 변경 상태·인계 자료·남은 자원을 적어 명시 반환한다. |
| `DONE` | 완료 조건과 필요한 독립 검토·수용 근거가 갖춰진 종료. 활성 범위를 반환하고 보존 자원은 명시한다. |
| `DEPENDENT` | 선행 완료·사람 결정이 없어 아직 착수할 수 없는 계획이다. |

소유권 변경은 당사자의 댓글 또는 당사자 지시를 인용한 대리 기록으로만 한다. 남의 PLAN을 보고 수락했다고 쓰지 않는다.
한 참여자는 현재 작업 외 **작은 다음 작업 1개 예약**을 권장한다. 다수 파일·자원을 미리 장기 선점하지 않는다.

## 착수·충돌·인계 절차

1. 양쪽 상황판, 우리 열린 `mail`, 작업큐 **전체 댓글**을 읽는다. GitHub API/CLI로 읽을 때 페이지 누락을 확인한다. 조회 예: `gh api --paginate repos/SongRoute/pitcheezy/issues/37/comments --jq '.[] | {id, body}'`.
2. 작업 ID와 완료 조건을 정하고, 기준 커밋·별도 worktree/브랜치·정확한 수정 파일·출력·실행 자원·비대상을 PLAN에 적는다. 범위 미정인 작업은 아직 CLAIM하지 않는다.
3. 선행 입력·권한·예약 소유자의 인계가 갖춰졌고 충돌이 없으면 CLAIM 댓글을 단다. 이후 댓글을 다시 조회해 자기 comment ID와 앞선 유효 CLAIM을 확인한 뒤 착수하며, 쓰기 직전 다시 조회한다.
4. 같은 작업 또는 겹치는 범위는 **GitHub REST 댓글 숫자 `id`가 가장 작은 유효 CLAIM**이 우선한다. 이는 링크의 `issuecomment-숫자`이며 GraphQL `IC_…` 문자열을 정렬하지 않는다. 기존 예약·유효 점유·게이트를 어긴 CLAIM은 무효이며 선착순이 이를 덮지 않는다.
5. 다른 작업 ID라도 유효 점유와 범위가 겹치면 새 CLAIM은 무효다. 뒤늦게 충돌을 발견한 작성자는 즉시 편집을 멈추고 변경을 보존한 뒤 RELEASE한다. 선행 RELEASE 이후에도 명시적으로 새 CLAIM하고 재조회해야 한다.
6. worktree가 달라도 동일 파일 병렬 편집은 하지 않는다. 넓은 폴더 예약과 세부 파일이 겹치면 기존 소유자가 먼저 범위를 좁히거나 넘겨야 한다. 읽기 전용 독립 검토는 병렬 가능하다.
7. 막히면 편집을 멈추고 BLOCKED에 현재 diff/커밋·실행 상태·필요 입력을 적는다. 인계 가능한 범위는 RELEASE하고 다른 비충돌 READY 작업을 CLAIM해 진행한다. 다른 사람이 이어받으려면 명시 RELEASE가 먼저다. 약속 시각 경과·무응답은 자동 탈취 근거가 아니다.
8. 검토에는 정확한 커밋·명령·증거를 넘긴다. 소스가 바뀌면 바뀐 범위의 검토를 갱신한다. 통합도 별도 소유자가 검토한 커밋만 가져온다.
9. DONE/RELEASE 뒤 지정 편집자가 #35 요약을 갱신한다. 기존 dirty·worktree·봉인 산출물은 보존하며 종료를 삭제 승인으로 해석하지 않는다.

GPU·MPS·메모리·포트·발행기·원격 경로·배포는 파일 소유권과 별도 자원이다. 작업큐 CLAIM은 기존 등록·독립 검토·장치/공통 lock을 대신하지 않는다.
맥 기록기·수집 프로세스에 신호를 보내지 않는다. 실자료 열람/실행, 외부 메시지, 팀원 레포 쓰기, 운영 교체 권한을 계획·우편·CLAIM으로 넓히지 않는다.
공개 댓글에는 비밀 값·접속 주소·개인 정보·개인 절대경로를 넣지 않는다. 파일은 저장소 상대경로, worktree는 식별자로 적는다. 필요한 비공개 정보는 위치 자체가 노출되지 않는 인계 표지만 적는다.

## 댓글 양식

```text
PLAN | CLAIM | REVIEW | BLOCKED | RELEASE | DONE — <작업 ID>
actor: Codex / session: <고유 ID> / at: YYYY-MM-DD HH:mm KST
state: READY | RESERVED | ACTIVE | REVIEW | BLOCKED | DONE
owner: <실제 소유자 또는 추천임을 명시> / prior: <선행 댓글 링크>
goal/done: <검토 가능한 완료 조건>
depends: <입력·결정·선행 작업> / base: <고정 커밋>
worktree/branch: <식별자> / write: <정확한 파일 목록, 없으면 none>
resources/output: <실행 자원·출력 범위, 없으면 none> / excludes: <비대상>
evidence: <커밋·검사·산출물·독립 검토 링크>
next/checkpoint: <다음 행동·필요 입력·확인 시각; 자동 만료 아님>
handoff: <dirty·동작 중 작업·보존 자원·반환 범위; 반환 시 필수>
```

## 도입 당시 초기 작업 계획 (이력)

아래는 도입 당시 계획이며 현재 소유권은 큐 댓글로 확인한다. READY의 담당은 **추천**이다.
Claude의 기존 출시 작업은 `legacy reserved`로 보호한다. 이는 기존 소유권 보존이며 현재 실행 중이라는 새 주장이 아니다. 새 체계 ACK와 정확한 범위 확인 전 재배정하지 않는다.
문서를 만들었다고 작업 중인 Claude가 자동으로 읽은 것은 아니다. 첫 `ACK | actor=ClaudeCode | session=… | CL-01/02/03 기존 범위 확인` 댓글로 수신과 범위를 확인하고 넓은 예약을 좁혀 병렬 가능한 범위를 연다. ACK는 배포·과학 승인과 무관하다.
