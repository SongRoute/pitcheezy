## 1. 개발 순서와 이번 연구의 목표

1. 현재 고정한 지원 범위에서 ML 예측 성능을 개선한다.
2. 연구 후보를 고정한 뒤 지원 투수를 확대하고, 기존/신규 투수 성능과 지원률을 따로 재검증한다.
3. 실제 CV 산출물을 인수한 뒤 의도·제구·사건 기여 분석을 확장하고 검증한다.
4. 팬 이해 평가와 그 결과에 따른 UI/UX 개발을 진행한다.
5. 경기 공급·지연·복구를 검증해 실경기에 운영한다.

현재 집중 대상은 **투구 결과 확률을 잘 예측하는 ML 모형**이다. 실제 선택 구종 맞히기는 별도 과제이며 추천 품질의 정답으로 쓰지 않는다. 논문 기반 예측 모델의 연구 후보 선정에는 예측 지표를 사용한다. 이는 서비스 추천 정책 채택과 다르며, 정책 우위에는 별도 독립 정책 평가가 필요하다. 목표 위치의 효과는 실제 의도 자료 없이 검증 완료로 표시하지 않는다.

‘최대한’은 무제한 탐색을 뜻하지 않는다. 데이터·모델·튜닝 예산을 고정한 묶음마다 개선과 실패를 남기고, 추가 개선의 근거와 비용을 검토해 다음 묶음을 정한다. 예산 내 최고 관측 성능과 일반화가 확인된 성능을 구분한다.

## 2. 논문 기준선과 지표

## 3. 공통 저울과 누수 방지

주 비교는 현재 서비스 계열의 **10개 투구 결과 분포**를 같은 적격 투구에서 예측한다. 기존 `src/pitcheezy`의 11-class RE24 실험 및 논문의 4/9/2-class 과제는 별도다. 레이블 매핑은 먼저 코드와 대조하고 누락·병합·제외 건수를 저장한다.

- 주지표: 투구 평균 NLL/cross-entropy. 보조: multiclass Brier(클래스 합, 범위 [0,2]), accuracy, macro-F1, 클래스별 precision/recall, 보정 곡선·ECE. 이진 과제는 ROC-AUC·PR-AUC도 남긴다. 클래스가 없으면 관련 지표는 null/이유를 기록한다.
- 경기·투수별 NLL, 구종·카운트·좌우·희귀 결과별 성능, 적격/지원/제외 분모를 함께 기록한다. 클래스가 많은 정답을 찍어 accuracy만 높이는 후보를 우수하다고 선정하지 않는다.
- 입력은 해당 판단 시점에 이용 가능한 상황·과거 기록과 평가할 후보 행동이다. 로그에 기록된 구종을 행동 조건으로 둔 결과 예측과 구종 자체 예측을 구별한다.
- 현재 공의 실제 구속·회전·도달 위치·타구/결과 정보는 투구 전 주 평가의 입력에 넣지 않는다. 조건부 물리 모형은 **TRAIN에서 얻은 동일 delivery 표본으로 적분**한다. 현재 실제 물리를 쓰는 원문 재현은 사후 조건부 예측 표에만 둔다.
- 데이터·정규화·범주/군집·빈도표·임베딩·타자 성향·최근 기록은 시점 경계를 지킨다. pitcher/batter 시즌 최종 집계나 뒤 경기 정보가 과거 예측에 섞이지 않는지 감사한다.
- TRAIN → 내부 시간 검증/조기 종료 → CAL(온도/혼합/분류 임계) → DEV → 최종 미열람 평가를 역할별로 분리한다. 경기와 타석이 경계에 걸리면 통째로 배정하며 purge 규칙을 명시한다. 시간 검증 밖에서 하이퍼파라미터를 선택하지 않는다.
- 기존 2024/2025 평가 구간과 July 2025 563구 진단은 이미 노출된 DEV다. 이름을 바꿔 새 holdout으로 취급하지 않는다. 두 연도 TRAIN/평가 중첩도 기록하고 독립 반복으로 합치지 않는다.
- **2026은 학습·튜닝·모델 선택 금지이며 이번 ML 연구에서는 추가 열람하지 않는다. 최종 평가셋도 개발에 쓰지 않는다.** 비2026 미열람 평가셋의 존재·노출 이력부터 메타데이터로 감사한다. 없으면 DEV 실험은 계속하되 ‘독립 일반화 확인 대기’로 남긴다.
- 현재 관측 후 지원/위치 결측 조건 때문에 제외된 표본이 있다는 점을 보존한다. 공통 교집합 점수와 전체 대상 지원률을 함께 보고, 후보가 어려운 표본을 버려 성능을 높이지 못하게 한다.

첫 실행 세션의 필수 목표는 **ML0 완료 + ML1 첫 비교 묶음 실행·기록**이다. 독립적인 baseline 구현은 병렬 진행하되 무거운 실행은 순차로 한다. 성능 문제가 아닌 구현 오류는 고친 뒤 새 run ID로 재실행하고 실패 기록도 남긴다. 모든 backbone을 거대한 조합으로 한꺼번에 돌리지 않는다.

탐색은 seeds `{0,1,2}`, 최종 연구 후보는 `{0,1,2,3,4}`. 모델별 HPO 상한과 총 accelerator 시간은 ML0 profile 후 후보 결과 전에 고정한다. 기본 첫 screen은 모델당 대표 설정 1개이며, 후속 HPO는 모델당 최대 8설정으로 시작한다. trial 수와 실제 계산량을 모두 공개한다. 중간 성능을 보고 특정 모델만 무제한 튜닝하지 않는다.

짝지은 경기 bootstrap 95% 구간, seed별 결과와 앙상블 결과를 모두 기록한다. 여러 후보 중 고르는 묶음은 비교군 보정 또는 별도 선정/확인 분할을 미리 정한다. 고정 예측의 bootstrap은 학습·CAL·모델 선택 불확실성 전체를 반영하지 않는다고 표시한다.

연구 후보 선정 규칙은 ML0에서 최소 실용 개선폭과 Brier·희귀 결과·지원률·비용의 허용 범위를 먼저 수치로 정한다. 주 NLL 개선과 guardrail을 통과한 후보만 개선으로 분류한다. 점추정만 낮거나 구간이 겹치면 ‘우열 미확정’, 명확한 악화는 ‘기각’이다. 동률이면 더 단순하고 빠른 모델을 다음 연구 기본값으로 삼을 수 있으나 성능 우위라고 부르지 않는다. 사전 계획한 두 연속 묶음에서 추가 개선 근거가 없으면 현재 최선과 남은 불확실성을 정리하고 확대 단계 진입 여부를 판단한다.

## 6. 실험 기록과 재현 번들

기존 저장소 규칙을 사용한다. ID는 `docs/experiments.md`와 configs를 확인해 충돌 없는 `EXP-P{phase}-{seq}`를 발급한다. 한 ID는 대조군 대비 변경 한 축이며, 묶음의 부모 ID/후속 관계를 기록한다.

- `configs/{ID}.yaml`: 가설, 기준선, 데이터/분할/피처/레이블 버전, backbone, 학습·중단·튜닝 예산, seeds, 지표·선정 규칙.
- SSD의 새 `{ID}/{seed}/`: 원자료를 가리키는 manifest, checkpoint, 전처리/보정기, 투구별 확률·정답키, 로그·환경·해시. 원자료를 덮어쓰지 않는다.
- `results/{ID}.json` 및 보고서: 기준선과 차이/구간, 클래스·선수·기간별 결과, 지원/제외 분모, 실패/중단, 시간·peak 메모리, 개선/악화/미측정, 선정/기각 이유.
- `docs/experiments.md`: 성공·실패를 포함한 한 행 요약과 결과 링크. 표본·지표가 다른 실험을 한 순위표에 섞지 않는다.
- 실행 시각, Git commit/dirty 여부, data/config/checkpoint SHA256, 라이브러리·장치·seed·명령·종료 코드, 연구 후보와 실제 서비스 모델 버전을 남긴다.
- 독립 검토자는 저장 예측에서 지표를 재계산하고, 일부 체크포인트 추론도 다시 확인한다. 미래정보·분할·물리 적분·보정·선정 편향과 실패 실험 누락을 검토한다.

## 7. GPU 판단

이번 확인: Apple M4, 통합 메모리 24 GiB; `.venv-observer-standalone`의 PyTorch 2.14.0에서 MPS build/available=true, CUDA=false. 기존 같은 장비의 평균 fit은 MLP 22.7초, Transformer 158.3초였고, 이 수치는 전처리와 최종 400표본 적분 추론을 제외한다. 출처는 위 시간 분할 비교 보고서다.

**첫 묶음에 외부 GPU 서버는 당장 필요하지 않다.** 이것은 과거 규모에 근거한 판단이며 새 모델의 실행 시간 보장은 아니다. ML0에서 전처리·fit·보정·적분 추론·저장 시간을 나눠 측정하고, 모델/optimizer/batch/activation을 포함한 peak 메모리와 CPU fallback을 확인한다. GBDT나 파일 입출력 병목에는 GPU를 추가해도 개선이 제한될 수 있다.

로컬 예상 한 실행이 2시간을 넘거나 메모리/필수 연산 지원을 초과하면 기존 예비 Colab Pro 또는 단일 CUDA GPU 환경을 검토한다. 필요한 VRAM은 profile로 산출하고 여유를 더해 선택한다. 초기부터 다중 GPU 서버를 전제로 하지 않는다. 데이터 전송·환경 설치·저장·비용을 포함한 구체적인 실행안을 만든 뒤 외부 자원을 사용한다. 이번에는 서버 신청·유료 실행·새 학습을 하지 않았다.
