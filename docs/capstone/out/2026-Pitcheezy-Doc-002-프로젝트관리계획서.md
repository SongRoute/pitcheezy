1. 프로젝트 개요

1.1 시스템 명칭 

AI 투구 추천 야구 관전 보조 시스템(Pitcheezy)

1.2 시스템 개요 

시스템은 MLB Statcast 투구 기록과 MLB 공식 경기 피드를 바탕으로, 투구 전 상황(볼카운트·주자·아웃·투수·타자)에서 수비 팀의 기대 승리확률을 가장 높이는 구종과 목표 구역 상위 3개를 추천한다.

사용자는 중계를 보면서 보조 화면(‘두 번째 전광판’)으로 추천을 확인하고, 실제 투구(구종·구속·도착 위치·판정)와 추천의 차이를 비교한다.

시스템은 추천 근거(선택 비중, 지원 여부, 추천 출처)를 함께 표시하고, 지원하지 않는 투수·상황은 숨기지 않고 ‘미지원’으로 알린다.

예측 성능(결과 확률 모델의 NLL·보정)과 추천 정책 효과(오프라인 정책 평가)는 분리해 검증하며, 2026 시즌 자료는 사전 등록한 정책 평가에만 쓴다.

2. 개발 프로세스  

2.1 프로세스 모형  

채택 모형 : 애자일(스크럼형 반복 개발) + 사전 등록 실험 게이트

채택 근거 :

  1) 추천 성능과 서비스 요구사항이 실험·실경기 결과에 따라 바뀌므로, 2주 안팎의 스프린트로 범위를 재검토한다.

  2) 예측 모델·추천 정책은 분할·지표·판정 기준을 먼저 커밋(사전 등록)한 뒤 결과를 열람해 선택 편향을 막는다.

  3) 계약 테스트(interfaces)가 텐서·추천·사건 분석 스키마를 코드로 강제해 모듈 간 통합 비용을 줄인다.

  4) 모든 설계 결정은 docs/decisions.md에 번호(D1~D179)로 기록해 되돌릴 때 근거를 남긴다.

2.2 개발 절차 

팀은 각 스프린트를 [그림 1]의 절차로 진행한다.

  스프린트 계획(백로그에서 스토리 선정) → 계약 테스트 작성 → 구현·실험(설정 파일로만) → 독립 검토·게이트 통과 → 스프린트 리뷰(시연·실경기 점검) → 회고와 결정 기록

팀은 실자료 실험을 실행하기 전에 등록하고, 작성자와 다른 에이전트·팀원이 독립 검토한다.

팀은 스프린트 종료 시 동작하는 결과물(모델·화면·운영 장치)을 확인하고 다음 스프린트 범위를 조정한다.

4. 프로젝트 운영 관리 

4.1 팀 미팅 계획  

(1) 정기 회의

팀 미팅 시간 : 매주 화요일 오후 4시

미팅시 토의 내용 : 개인별 수행 결과 보고, 실험·실경기 점검 결과 공유, 문제점과 해결 방안 토의

미팅 참석자 : 지도교수, 팀장, 팀원

(2) 비정기 회의

팀장 또는 지도교수는 프로젝트 진행에 문제가 생기면 비정기 회의를 소집한다.

팀원은 GitHub 이슈(상황판 #35, 작업큐 #37)와 우편 라벨로 비동기 협의를 기록한다.

(3) 프로젝트 발표 미팅

팀은 캡스톤 디자인 교과목의 중간 발표와 최종 발표를 진행한다.

팀은 2026-10-06 지도교수 시연(저장 경기 재생, 약 5분)을 수행했고, 2026년 11월 말 전시(포스터 시안 10/31 제출)를 준비한다.

4.2 Ground Rules  

1. 팀원은 개발 일정을 지키고, 지연이 생기면 회의에서 사유를 바로 보고한다.

2. 팀원은 정기 회의에 불참할 경우 팀장에게 미리 알린다.

3. 정기 회의에 지각한 팀원은 다음 회의에 간식을 준비한다.

4. 팀원은 모든 실험을 설정 파일(configs/)로 정의하고, 결과에 시드·데이터 버전·커밋을 기록한다.

5. 팀원은 실험 결과를 열람하기 전에 분할·지표·판정 기준을 커밋(사전 등록)한다.

6. 팀원은 2026 시즌 자료를 학습·튜닝·모델 선택에 쓰지 않는다.

7. 팀원은 코드 병합 전에 계약 테스트(pytest)를 통과시키고, 작업 인계 시 인계 문서를 갱신한다.

8. 팀원은 설계를 바꿀 때 docs/decisions.md에 결정 한 줄을 먼저 적는다.
