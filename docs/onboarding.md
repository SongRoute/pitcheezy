# 신규 팀원 온보딩

소유: 통합 문서 담당 · 갱신: 진입 명령·권한 경로 변경 시 · 갱신일: 2026-11-01.

[시작](../README.md) → [운영 안내](pm/overview.md) · [프로젝트 지도](pm/project-map.md). 현재 전시 방향은 [10/31 인계 §2·§5](handoffs/CODEX-resume-2026-10-31.md)를 읽는다. 과거 문서의 일정·역할·자원 승인을 현재 작업 권한으로 해석하지 않는다.

## 첫 작업 순서

1. 담당자와 이 작업의 저장소·정확한 브랜치/커밋·공개/비공개 범위를 확인한다. 공개 clone만으로 비공개 모델·자료까지 재현되는 것은 아니다.
2. [작업큐 절차](pm/work-queue.md)와 현재 작업 지시를 대조해 파일·자원 소유권을 확인한다. 외부 게시가 금지된 작업은 큐를 읽고 담당자에게 충돌을 알린다. 다른 작업의 점유·dirty 파일을 임의로 정리하지 않는다.
3. 별도 worktree에서 `git status --short`, `git branch --show-current`, `git rev-parse HEAD`를 기록한다. 한 작업은 한 브랜치·한 PR로 진행하고 검토·통합 담당을 확인한다.
4. [환경 재현 안내](onboarding-environment.md)의 합성 CPU 검사부터 실행한다. 명령·출력·Python 버전·커밋을 남기고, 자료 수집·학습·서버 기동으로 범위를 넓히지 않는다.
5. [격자 계약 검사](../tests/interfaces/test_grid.py)와 [구현](../src/pitcheezy/interfaces/grid.py)의 입력·출력·좌우·단위를 설명해 본다. 이 계약 검사는 전시 G0의 실제 지원 범위나 예측 성능을 증명하지 않는다.
6. 변경 파일·완료 조건·검사·필요 자료를 적은 작은 작업안으로 시작한다. 실자료 작업은 [공통 계약](pm/contracts.md)의 등록·독립 검토·자료 역할 게이트를 따른다.

## 앱·자료로 넘어가기 전

모델·자료 없이 위 절차까지 진행할 수 있다. 실제 앱은 [Observer 안내](../apps/observer/README.md)와 담당자에게 모델/자료 manifest·접근 권한·빈 포트·새 출력 위치를 확인한 뒤 기동한다. 기존 8766/8771/8775 실행 스크립트를 첫 실습으로 실행하지 않는다.

자료 경로가 보여도 열람·학습·재배포 권한이 생기지 않는다. 2026 자료로 학습·튜닝·모델 선택을 하지 않으며, 봉인 결과·기록기·기존 운영 자원을 보호한다. [현장 인벤토리](pm/operations-inventory.md)의 경로·계정 정보를 공개 복사하지 않는다. 문서 정리는 push·운영 교체 승인이 아니다.

2026-10-06의 환경·공개 main 관측은 [변경 전 원문](https://github.com/SongRoute/pitcheezy/blob/6e2038fd0010657e6f6f2d1e49820490f6195da4/docs/onboarding.md)에 보존한다. 당시 수치를 현재 checkout의 결과로 재사용하지 않는다.
