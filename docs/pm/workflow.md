## 작업 상태

제안 → 준비 → 실행 가능 → 진행 중 → 검증 중 → 완료. 별도 상태 `막힘`에는 이유·필요한 입력·재개 조건을 쓴다. 완료는 반환 메시지가 아니라 커밋/diff·검사 출력·산출물 검토 후 PM 수용으로 정한다.

각 작업에는 ID, 책임 PM, 실제 작업자/모델/선정 이유, 기준 커밋·worktree, 파일 소유권, 완료 조건, 자원·선행 조건, 결과·검토 링크, 다음 작업을 기록한다. 착수·종료·막힘·인계 시 갱신하고 관측 시각을 KST로 적는다. 프로세스가 없으면 `실행 중`이라고 쓰지 않는다.

작성자와 검토자는 분리한다. 같은 모델의 다른 작업자는 별도 작업자 검토이지 독립 모델 검토가 아니다. 기존 과학 게이트에서 다른 모델을 요구하면 실제 모델을 확인해 충족하거나 미충족으로 남긴다.

## 자율 범위와 인계

일상 구현·검사·승인 범위의 후속 실험 설계와 등록은 담당 PM이 진행한다. 모델의 공식 승격·정책 채택·평가 경계 변경·운영8766 교체는 기존 과학/운영 게이트와 Song 권한을 유지한다. 시연 수정 허용은 과학 판정 변경이나 운영 전체 교체 허용이 아니다. push/PR merge는 이번 전환 범위 밖이다.

연구→서비스: 후보 묶음 제출 → 서비스 인수 → 격리 통합 검증 → 통합 PM 수용/재작업. 개발 자료 개선만이면 `통합 가능성 검증 후보`로 쓰고 운영 승격으로 과장하지 않는다. 서비스→연구: 경기/투구 키·재현 입력·코드·오류·지원 범위를 전달한다. 평가 사례를 자동으로 학습 자료에 편입하지 않는다.

별도 세션은 공통 파일과 고정 커밋으로 연결한다. worktree 문서는 자동 동기화되지 않으므로 공유 문서의 정본은 `/Users/song/Projects/pitcheezy/docs/pm`이다. 다른 세션으로 넘길 때 기존 작성자 종료·변경 상태를 먼저 확인하고 소유자 교체를 기록한다. 활성 채팅의 존재를 작업 실행 증거로 쓰지 않는다.


## 정본 우선순위와 읽는 순서

사용자의 최신 명시 지시와 적용되는 상위 실행 지침을 우선한다. repo 안에서는 AGENTS/CLAUDE/AI_COLLABORATION의 최신 날짜 규칙 → 공통 계약·공식 결정 → 분야별 현재 상태와 해당 작업의 고정 source/config/manifest/receipt 순으로 대조한다. 문서 최신 날짜만으로 봉인된 실험 계약을 덮지 않는다. 상충하면 담당 PM이 영향·근거를 기록해 해소한다.

README는 안내, overview는 역할, 이 문서는 작업 방법, contracts는 분야 경계, resources는 자원 사용 규칙, operations-inventory는 실제 배치/관측/보존, 각 state는 관측 시각이 붙은 현재 상태를 맡는다. roadmap/design/plan은 장기 방향·설계 배경이며 즉시 실행 큐로 읽지 않는다. SESSION_HANDOFF·handoffs·지난 보고서는 이력이다. 실제 실행 주장은 config/manifest/로그/receipt로 확인하고 graphify는 탐색 보조로만 쓴다.

## 작은 작업의 실행 순서

1. **작업 정의:** ID·요청·소유자·기준 commit/dirty·파일 범위·완료 조건·비대상·예산/중단 조건을 기록한다. 기존 구현/표준 도구부터 찾는다.
2. **계약 확인:** 연구면 데이터 분할·등록·seed·예산·fresh output/lock, 서비스면 피드/공 키·시각·입출력·지원/오류 상태·자료 권한·rollback을 고정한다.
3. **작은 경로 구현:** 한 입력이 결과까지 도달하는 최소 변경을 별도 worktree에서 만든다. 연구 실행과 서비스 런타임을 섞지 않는다. 실제 입력 권한이 없으면 합성 계약 검사로 가능한 범위를 명시한다.
4. **검증/독립 검토:** 의미 있는 최소 회귀와 필요한 실제 기기 종단 검증을 수행한다. 테스트 통과·등록·실행·과학 판정·운영 적용을 별도 상태로 보고한다.
5. **통합:** 검토한 정확한 commit/diff만 지정 작업자가 통합한다. 다른 dirty나 봉인 artifact를 포함하지 않는다. 새 source와 이전 실행 source를 혼동하지 않는다.
6. **작업 종료/보존:** 작업자가 worktree의 `preserve` 또는 `remove-proposed` disposition, 최종 source·diff·evidence 링크, 다음 소유자를 남긴다. `remove-proposed`는 삭제 승인이 아니다. 실행/봉인 source 의존 및 미통합 변경 확인과 개별 소유자 수락 전에는 제거하지 않는다. 과거 worktree 일괄 삭제에 소급 적용하지 않는다.
7. **릴리스/복구:** 별도 운영 권한 아래 백업·serving hash·runtime source·세션/DB 보존·관측·rollback 증거를 남긴다. 배포 후 수용 실패면 정해진 복귀 경로를 사용하고 원인·잔여 위험을 기록한다.

## 단계별 필요 조건과 공동 수용 기준

아래는 운영상 수용 기준이다. 모든 미래 장애 방지나 통계·과학적 우위를 수학적으로 보장한다는 뜻이 아니다. 단계의 조건을 **함께** 충족하고 독립 검토와 담당 PM 수용이 있어야 다음 단계로 이동한다.

| 단계 | 빠지면 안 되는 조건 | 함께 충족했을 때 수용할 범위 |
|---|---|---|
| 착수 | 단일 소유·기준/dirty 보존·자료/자원 계약·유한 완료 조건 | 그 작은 작업의 준비/구현 시작 |
| 구현 검토 | 재현 가능한 diff·계약 검사·실패 경로·잔여 한계 | 검토한 source의 격리 통합 가능성 |
| 연구 실행 | exact 등록·분할/seed/예산·불변 source/data·fresh claim/output·장치 배타·중단 감독 | 해당 attempt만 실행; 결과 성공/승격은 별도 |
| 기능 수용 | 정확한 공 상태·투구 전 입력/누수 방지·실제 기기 E2E·오류/지연/미지원 표시 | 검증된 입력·기기·범위의 기능 완료 |
| 공개/운영 | 기능 수용·데이터/관리 권한·복구/rollback·부하/관측·지원 분모·명시된 release GO | 정한 범위 공개; 신규 모델/정책 우위 승인 아님 |

2~3일 점검에서 속도는 코드량이 아닌 실제 기기 E2E 검증 완료로 센다. 빠르면 추가 후보를 순차 검토하고 늦으면 기본 기능을 줄여 완성한다. 정확성·누수 방지·권한·복구 조건은 기능 축소로 면제되지 않는다.
