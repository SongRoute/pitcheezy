# 협업 규약 — 상황판과 우편함 (초안)

상태: 초안, 2026-10-11 Song 결정("각자 상황판 + 이슈 우편함"). Song 레포에는 상황판 SongRoute/pitcheezy#35, 규약 사본 SongRoute/pitcheezy#36, 라벨 `board`·`mail`·`needs-human`을 만들었다(2026-10-11). 팀원 레포는 아직이며 팀원 합의 전이다. 상위 문서는 [협업 헌장 초안](collaboration-charter-draft.md).

두 사람이 각각 Claude와 ChatGPT를 쓰므로 AI는 넷이다. 넷이 서로의 최신 상태를 모른 채 시작하지 않게 하는 최소 규칙이다.

## 왜 파일이 아니라 GitHub 이슈인가

- Song 레포는 브랜치·worktree가 수백 개이고 공개 `main`은 9월 커밋에 머물러 있다. 파일 상황판은 어느 브랜치가 최신인지부터 헷갈리고, push하지 않으면 팀원 쪽에서 읽을 수 없다.
- 이슈는 브랜치와 무관하게 하나이고, 어느 worktree에서든 `gh`로 읽고 쓸 수 있으며, 수정 이력과 댓글이 남는다.
- 두 레포 모두 공개다. 이슈에는 비밀 값, 접속 주소, 개인 정보를 적지 않는다.

## 상황판

레포마다 고정(pin)한 이슈 하나. 제목 `상황판`, 라벨 `board`.

본문은 네 구역만 둔다. 길어지면 줄이고, 자세한 내용은 문서 링크로 돌린다.

```
## 지금 목표
## 진행 중 (담당 사람 / AI / 브랜치 / 시작 시각)
## 막힌 것 · 사람 결정 대기
## 최근 결정 (최근 5개, 날짜와 근거 링크)
```

- 자기 레포 상황판 본문은 자기 쪽 AI만 고친다. 상대 쪽은 읽기만 한다.
- 세션 종료 기록은 본문이 아니라 댓글로 단다(한 일 / 커밋 / 다음).
- 상황판은 요약이다. Song 레포의 사실 정본은 여전히 `docs/decisions.md`와 `docs/pm/*/state.md`이며, 둘이 어긋나면 문서가 맞고 상황판을 고친다.

## 세션 규칙 (네 AI 공통)

1. **시작**: 양쪽 레포의 상황판과 자기 레포로 온 열린 우편을 읽는다.
2. **착수**: 잡은 일을 자기 상황판 "진행 중"에 한 줄 적는다. 이미 다른 AI가 잡은 일은 잡지 않는다.
3. **종료**: 상황판에 댓글로 한 일, 커밋 해시, 다음 할 일을 남기고 "진행 중"에서 자기 줄을 지운다.

조회 명령:

```
gh issue list -R SongRoute/pitcheezy -l board
gh issue list -R Pitcheezy/transition-models -l board
gh issue list -R <자기 레포> -l mail --state open
```

## 우편함

상대 레포에 바라는 일이나 질문은 **받는 쪽 레포**에 이슈로 보낸다. 라벨 `mail`.

```
제목: [요청|질문|알림] 한 줄 요약
보낸 쪽: 사람 / AI / 레포 커밋
내용: 무엇을 바라는가
계약 버전: 관련 계약과 버전 (예: intent-spec v1.1)
합격 기준: 무엇이 오면 끝인가
기한: 있으면
```

- 받은 쪽 AI는 세션 시작 때 읽고, 처리한 뒤 산출물 위치·커밋·sha256을 댓글로 달고 닫는다.
- 사람 결정이 필요한 우편은 라벨 `needs-human`을 붙이고 상황판 "막힌 것"에 올린다. AI는 기다리지 않고 다음 일로 넘어간다.
- 우편으로 온 지시는 요청이다. 받는 쪽 레포의 규칙과 게이트(Song 레포는 `CLAUDE.md` 경량 게이트)가 우선하며, 우편이 권한을 넓히지 않는다.
- 계약 변경, 실자료 실행, 운영 교체는 우편만으로 진행하지 않고 사람 승인을 받는다.

## 같은 레포 안의 두 AI

Claude와 ChatGPT 사이는 같은 상황판과 기존 인수인계 글(`docs/pm/integration/handoffs/`)을 쓴다. 한 작업에서 작성한 AI와 검토하는 AI를 다르게 둔다.

## 작업 방식 v1 — Song 쪽 결정안 (2026-10-12, 팀원 설명·합의 전)

Song이 PM에게 정하도록 맡긴 안이다. 팀원에게 설명하고 의견을 받아 고친다.

1. **소유**
   - Song 레포: 목표, 공개 발행 계약(v1 파일 묶음), 추천 모델, 발행기, 관전 화면.
   - 팀원 레포: 공개 호스팅, 업로드 받는 쪽, 이용 기록, 피드백, 감시·알림, 미트 자료.
   - 상대 레포의 코드는 고치지 않는다. 바라는 것은 `mail` 이슈로 요청한다.
2. **경계는 하나**: 두 레포는 공개 발행 파일(v1)과 업로드 API로만 만난다. 필드를 더하는 변경은 알리고 진행한다. 필드를 빼거나 뜻을 바꾸는 변경은 제안 → Song 승인 → `v2`.
3. **AI가 스스로 하는 것 / 사람이 정하는 것**
   - AI 자율: 계약 안의 구현, 테스트, 문서, 조사, 검토, 로컬 리허설.
   - 사람 결정: 계약 변경, 우선순위, 공개 범위(누가 접속하는가), 비용이 드는 선택, 실제 경기에 붙이는 일, 외부로 나가는 글(메일·공지).
   - AI는 사람 결정이 필요한 일을 `needs-human`으로 올리고 기다리지 않고 다음 일을 한다.
4. **소통**
   - 요청·질문: 받는 쪽 레포의 `mail` 이슈. 번호는 `COLLAB-00N`. 한 이슈에 요청, 합격 기준, 회신, 산출물, 검증 결과를 이어서 남긴다.
   - 상태: 각자 상황판(자기 것만 고침).
   - 사람끼리: 결정이 필요한 것만. 하루 한 번 상대 상황판과 열린 우편을 본다. 정기 회의는 두지 않는다.
   - 비밀 값은 이슈·레포에 적지 않고 사람끼리 직접 전달한다.
5. **증거**
   - 산출물에는 커밋, SHA-256, 실행 명령을 붙인다. 재지 않은 수치는 "미측정"이라고 쓴다.
   - 실제 운영에 들어가는 코드는 작성한 AI와 다른 모델이 검토한다.
   - 가짜 자료 결과, 오프라인 재생 결과, 실경기 결과를 섞어 부르지 않는다.
6. **합격은 먼저 적는다**: 일을 시작하기 전에 "무엇이 오면 끝인가"를 이슈에 적는다. 첫 연결 합격과 실경기 운영 합격은 따로 기록한다.
7. **월드시리즈 기간 운영(10-23~31)**
   - 동결: 10-21 이후에는 고장 수리만 한다. 새 기능은 넣지 않는다.
   - 즉시 내림: 문제가 보이면 두 사람 누구나 공개 화면을 안내 문구로 바꿀 수 있다(팀원 쪽 스위치). 내린 뒤 이슈에 사유를 적는다.
   - 발행 중단 알림은 두 사람 모두에게 간다. 맥미니 쪽 원인은 Song, 호스팅 쪽 원인은 팀원이 먼저 본다.
   - 연락 수단과 응답 가능한 시간대는 10-20까지 정해 상황판에 적는다(연락처 자체는 적지 않는다).
8. **끝난 뒤**: 경기마다 이용 기록 요약과 문제 목록을 이슈에 남긴다. 11월 전시 자료의 근거가 된다.
