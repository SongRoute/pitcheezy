## 1. 문제 — 야구 팬이 궁금한 세 가지

다음 공을 기다리는 순간에는 선택의 이유가 궁금하고, 공이 들어온 뒤에는 예상과 실제가 어떻게 달랐는지 궁금하다. 중요한 결과가 나왔을 때는 작전과 실행을 구분해 이해하고 싶다.

| 팬의 질문 | 포스터에서 말할 내용 | 현재 표시할 상태 |
|---|---|---|
| 다음 공은? | 지원 범위의 추천과 보류 이유를 보여 준다. 미지원 투수의 기록 참고 카드는 추천·예측과 구분한다. | 출시 후보 구현·부분 검증; 추천 가치 우위 입증은 별도 |
| 실제 공은? | 실제 구종·위치·결과와 추천 당시 내용을 구분해 비교하도록 한다. 누락·정정·미확인은 별도로 표시한다. | 출시 후보 구현·부분 검증; 최신 실기기 검증은 미완 |
| 중요한 결과는 왜? | 작전·투수 실행·타자 수행·교체 판단의 기여를 근거와 함께 설명하는 것이 목표다. | 검증된 통합 기능은 미완; 이번 감사에서 완료 근거 미확인. 기여율을 임의로 넣지 않음 |

[그림 A 자리] 같은 장면의 “투구 전 추천/보류 → 실제 기록 비교” 두 화면. 최종 고정 빌드·같은 투구 ID·공개 가능한 생성자료/허용된 기록의 승인된 캡처로 채운다. 참고 카드에는 “기록 참고, 추천 아님”을 보이게 한다. 현재 캡처 미확보.

## 2. 현재 만든 것 — 구현과 실제 운영을 구분

- 경기 정보를 공개 파일로 발행하고 팬 화면이 이를 읽는 구조, 정정·미확인 상태 처리와 불필요한 재쓰기 감소를 구현했다.
- 지원하지 않는 투수는 근거가 부족한 추천 대신 과거 기록의 참고 카드를 표시하는 경로를 준비했다.
- 자동 시작·재시작과 이상 알림 부품, 조건부 업로드·접근 제어·회수 절차를 준비했다. 실제 서비스 전체 운영 완료를 뜻하지 않는다.
- 선택 참여 세션·활성 시간·의견 수집/집계 부품은 있다. 실제 뷰어 연결·수집 활성화·운영 추출은 아직 별도다.
[그림 B 자리] “경기 입력 → 발행기 → 공개 파일 호스트 → 팬 화면” 4칸 구조. 팬 요청이 맥 발행기로 직접 들어오지 않는 경계와 로컬 검증/실배포 구분을 표시한다. 최종 source/build/배포 version 근거로 확정한다.
