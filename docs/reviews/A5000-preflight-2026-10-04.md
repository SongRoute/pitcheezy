## Shapes (metadata) and size estimate

Per row: tokens `[6,38] f32` 912 B, valid `[6] bool` 6 B, context `[52] f32` 208 B,
workload `[4] f32` 16 B, keys `[3] i64` 24 B, y/game_pk/pitcher `i64` 24 B, date `i32`
(YYYYMMDD, for the server-side 2026 recheck) 4 B = 1,194 B
(`export_cuda_direct.estimate_bytes`, unit-tested).

- train 1,252,824 rows → 1,495,871,856 B
- earlystop (May 1-15) 16,000 → 19,104,000 B
- temperature (May 16-31 Cpanel) 2,603 → 3,107,982 B
- blend (June Cpanel) 4,821 → 5,756,274 B
- dev (Cpanel) 12,334 → 14,726,796 B
- mlb_dev (frozen whole-MLB) 311,721 → 372,194,874 B
- **total 1,600,303 rows → 1,910,761,782 B (≈1.91 GB, 1.78 GiB)** + manifest (KB)

Uncompressed `.npy` (mmap-able, no pickle). The exporter recomputes this from real
shapes and refuses to write if it differs from `--expect-bytes 1910761782`.
GPU memory per fit: train tensors ≈1.45 GB on device + model/optimizer (<10 MB); one
fit per GPU at a time.

## Limitations

- Not run: real export, GPU check/smoke, any CUDA fit. CUDA binding (`bind_gpu`)
  and UUID verification via `get_device_properties(0).uuid` are untested on CUDA.
- CUDA results are not bit-comparable to the MPS EXP-P15-001 control; the CUDA
  control arm is the only valid comparator. CUDA kernels may be nondeterministic
  (CUBLAS_WORKSPACE_CONFIG set per process, deterministic algorithms not forced).
- Temperature/June-blend semantics are reused exactly (temperature on server, June
  blend + mix on the Mac with frozen G0 MPS members and parent baseline); the mix
  therefore combines a CUDA direct member with an MPS G0 member — descriptive only.
- Residual/periodic arms reuse their frozen networks without workload columns; they
  compare to the CUDA control, not to their own DRAFT Mac families.
- Export peak RAM and wall time are unmeasured; real parent loader not exercised here.
- The queue holds GPU locks in `<queue-dir>/locks` unless `--lock-dir` is shared; it
  does not see GPU use by other users (root should check `gpu st` before starting).
