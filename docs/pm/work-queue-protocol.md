# 착수·충돌·인계 절차

상위: [공동 작업큐](work-queue.md) · 양식: [댓글·로컬 기록](work-queue-template.md)

현재 사용자가 발신을 금지한 경우 아래 댓글 작성 단계는 수행하지 않는다. 전체 큐 읽기·충돌 확인과 로컬 범위 기록만 하며 원격 선점 완료라고 쓰지 않는다. 이 예외는 기존 소유권을 취소하거나 자료·운영 게이트를 면제하지 않는다.

1. 양쪽 상황판, 우리 열린 `mail`, 작업큐 **전체 댓글**을 읽는다. GitHub API/CLI로 읽을 때 페이지 누락을 확인한다. 조회 예: `gh api --paginate repos/SongRoute/pitcheezy/issues/37/comments --jq '.[] | {id, body}'`.
2. 작업 ID와 완료 조건을 정하고, 기준 커밋·별도 worktree/브랜치·정확한 수정 파일·출력·실행 자원·비대상을 PLAN에 적는다. 범위 미정인 작업은 아직 CLAIM하지 않는다.
3. 선행 입력·권한·예약 소유자의 인계가 갖춰졌고 충돌이 없으면 CLAIM 댓글을 단다. 이후 댓글을 다시 조회해 자기 comment ID와 앞선 유효 CLAIM을 확인한 뒤 착수하며, 쓰기 직전 다시 조회한다.
4. 같은 작업 또는 겹치는 범위는 **GitHub REST 댓글 숫자 `id`가 가장 작은 유효 CLAIM**이 우선한다. 이는 링크의 `issuecomment-숫자`이며 GraphQL `IC_…` 문자열을 정렬하지 않는다. 기존 예약·유효 점유·게이트를 어긴 CLAIM은 무효이며 선착순이 이를 덮지 않는다.
5. 다른 작업 ID라도 유효 점유와 범위가 겹치면 새 CLAIM은 무효다. 뒤늦게 충돌을 발견한 작성자는 즉시 편집을 멈추고 변경을 보존한 뒤 RELEASE한다. 선행 RELEASE 이후에도 명시적으로 새 CLAIM하고 재조회해야 한다.
6. worktree가 달라도 동일 파일 병렬 편집은 하지 않는다. 넓은 폴더 예약과 세부 파일이 겹치면 기존 소유자가 먼저 범위를 좁히거나 넘겨야 한다. 읽기 전용 독립 검토는 병렬 가능하다.
7. 막히면 편집을 멈추고 BLOCKED에 현재 diff/커밋·실행 상태·필요 입력을 적는다. 인계 가능한 범위는 RELEASE하고 다른 비충돌 READY 작업을 CLAIM해 진행한다. 다른 사람이 이어받으려면 명시 RELEASE가 먼저다. 약속 시각 경과·무응답은 자동 탈취 근거가 아니다.
8. 검토에는 정확한 커밋·명령·증거를 넘긴다. 소스가 바뀌면 바뀐 범위의 검토를 갱신한다. 통합도 별도 소유자가 검토한 커밋만 가져온다.
9. DONE/RELEASE 뒤 지정 편집자가 #35 요약을 갱신한다. 기존 dirty·worktree·봉인 산출물은 보존하며 종료를 삭제 승인으로 해석하지 않는다.

GPU·MPS·메모리·포트·발행기·원격 경로·배포는 파일 소유권과 별도 자원이다. 작업큐 CLAIM은 기존 등록·독립 검토·장치/공통 lock을 대신하지 않는다.
맥 기록기·수집 프로세스에 신호를 보내지 않는다. 실자료 열람/실행, 외부 메시지, 팀원 레포 쓰기, 운영 교체 권한을 계획·우편·CLAIM으로 넓히지 않는다.
공개 댓글에는 비밀 값·접속 주소·개인 정보·개인 절대경로를 넣지 않는다. 파일은 저장소 상대경로, worktree는 식별자로 적는다. 필요한 비공개 정보는 위치 자체가 노출되지 않는 인계 표지만 적는다.
