# 추천 구종과 실제 구종 불일치 초기 진단

2026-09-23, 코드 기준 `1926234`. 사용자는 UI가 친화적이지 않고 정보가 과밀하다고 지적했다. UI 전면 수정은 후속으로 남기되 추천과 실제 구종의 큰 차이를 먼저 점검했다. 추천 모형·UI·원자료는 변경하지 않았다.

## 확인한 관측

활성 `C-D-FULL-001/observer.sqlite3`를 읽기 전용 트랜잭션으로 읽었다. 세션별 `cursor`까지 이미 공개한 공만 대상으로 해당 `pitch_id`의 저장 추천을 실제 기록과 비교했다. 같은 공의 반복 세션은 중복 제거했으며 추천 ID 충돌은 없었다. 조회 당시 21개 세션, 고유 공개 공 16개다. 자동 QA와 사용자 관전이 섞인 편의 표본이므로 다음 수치는 전체 성능이나 정책 품질 평가가 아니다.

| 항목 | 관측 |
|---|---:|
| 추천 준비/실제 구종 확인 가능 | 16/16 |
| 첫 추천 구종과 실제 구종 일치 | 4/16 (25%) |
| 상위 3개 행동 중 실제 구종 포함 | 8/16 (50%) |
| 상위 3개 행동이 모두 같은 구종 | 8/16 |

상위 3개는 서로 다른 **구종** 세 개가 아니라 **구종×구역** 행동 세 개다. 실제는 SI 10, FF 3, ST 2, SV 1구; 첫 추천은 ST 6, CH 4, SI 4, SV 1, FF 1구였다. 게임 776703의 타석 2는 공개된 6구 모두 첫 추천과 실제 구종이 달랐다. 같은 경기 타석 8의 공개된 3구는 모두 같았다. 표본 선택에 민감하므로 일반화하지 않는다.

구체적으로 Webb–Díaz의 3–0 공 `776703:2:4`는 실제 싱커, 첫 추천 체인지업이었다. 표시된 2위는 같은 중앙 구역의 싱커이며 1위와의 모델 WE 차이는 **0.024026 %p**다. 이는 작은 점추정 차이로 순위가 갈렸다는 뜻이며 통계적 동률·유의성·실제 개선을 입증하지 않는다. 다른 사례 `776703:3:2`도 실제 포심이 2위이며 체인지업과의 차이는 0.017331 %p다.

UI `App.tsx:226–228`은 비교 모드에서 선택한 공의 저장 추천을 사용한다. 기존 실제 브라우저 검사와 이번 동일 ID 점검에서 앞뒤 공을 잘못 붙이는 증거는 발견하지 못했다. 사용자의 모든 조작을 관측한 것은 아니다.

## 코드와 기존 평가에서 확인한 한계

- `recommender.py:205–227`/동결 `planner.py`는 타석 내 상태 전이를 거친 초기 수비팀 WE의 최대값으로 후보를 정렬한다. 실제 다음 구종의 발생 확률을 예측하는 모델이 아니다. 레퍼토리 빈도는 지원 후보와 비교 기준 정책에 쓰이며 추천 순위에 직접 배합 제약을 주지 않는다.
- `recommender.py:174–177`의 6개 입력 토큰 중 후보 공 하나만 valid다. 직전 공/같은 타석 배합 이력은 현재 Observer 추천에 들어가지 않는다. 카운트는 반영하지만 구종별 최근 사용 횟수는 카운트별 배합 분포가 아니다.
- 기존 도달 위치에 Gaussian 가중치를 주어 목표 구역을 근사한다. 실제 의도/제구 오차를 식별한 분포가 아니다. 이번에는 이 제약을 CV를 기다리는 이유로 삼지 않고 불확실성으로 기록한다.
- 작은 값 차이도 결정적인 1위가 된다. 현재 화면은 후보 순위의 통계적 안정성이나 선수별 배합 적합성이 검증됐음을 뜻하지 않는다.
- 기존 S1의 NLL/Brier는 공 결과 분포에 대한 지표다. 실제 다음 구종 일치율이나 추천을 따랐을 때의 승률 개선 검증이 아니다. 정책 가치/OPE는 계속 미측정이다. 작동/저장/UI 검증 완료와 추천 품질 완료를 구분한다.

불일치만으로 추천 오류를 확정할 수 없지만, 위 한계 때문에 불일치를 전략적 우월성으로 설명할 근거도 없다. 이 구조가 현재 차이에 각각 얼마나 기여했는지는 아직 측정하지 않았다.
