# PM이 쓸 도구 조사 (2026-10-03)

방법: 2026-10-02 밤~10-03 새벽, 에이전트 5개가 공식 문서(code.claude.com), 웹, 이 맥의 설치 상태를 읽기 전용으로 조사했고, 별도 검증 에이전트가 기능 주장 35개를 공식 문서와 대조했다(34개 확인, 1개는 공개 문서에 없음). 그 뒤 준비 세션이 핵심 두 가지를 이 맥에서 직접 시험했다.
표기: **문서** = 공식 문서에서 확인, **시험** = 이 맥에서 실제로 해 봄, **관찰** = 이 맥의 설정·앱에서 봄, **미확인** = 확인 못함.

## 1. 새 방식의 전제 — 되는가
- **작업자를 Opus 5.5로 고정** (문서 + 시험)
  - 방법: Agent 도구에 `model: "opus"`를 넘기거나, `.claude/agents/<이름>.md`의 `model: claude-opus-5-5`.
  - 모델이 정해지는 순서: 호출 때 넘긴 값 → 정의 파일 → 환경변수 `CLAUDE_CODE_SUBAGENT_MODEL` → 메인 세션 모델.
  - 시험(10/3 00:40): Fable 세션에서 `model: "opus"`로 부른 하위 에이전트가 Opus 5.5(`claude-opus-5-5`)로 떴다. 정의 파일 경로는 시험 안 함.
  - 주의: 이 맥의 사용자 기본 모델이 Fable이라, 위 순서대로라면 모델을 적지 않은 작업자는 Fable로 뜬다(시험 안 함).
- **하위 에이전트의 재귀 호출** (문서 + 시험)
  - 문서: 기본으로 메인 세션 아래 3층까지. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`로 바꾼다.
  - 시험: 작업자(1층)에게 Agent 도구가 있었고, 그 작업자가 부른 하위 에이전트(2층)도 Opus 5.5로 답했으며 Agent 도구가 있다고 보고했다. 앞에서 기다리는 실행과 뒤에서 도는 실행 둘 다 됐다.
  - 하위 에이전트에게는 Workflow 도구가 없다. 워크플로는 PM만 돌릴 수 있다.
  - 동시 실행 한도는 세션당 20개(`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`).
- **PM이 다른 세션에 지시** (문서)
  - SendMessage와 ListAgents로 이미 열려 있는 세션에 메시지를 보낸다. `notify_when_idle`로 끝남 알림을 받는다.
  - 다른 세션이나 에이전트가 전한 "승인"은 승인으로 인정되지 않는다. 내 세션에서 막힌 일을 다른 세션에 시키는 것도 금지다.
- **PM이 새 세션을 직접 만들기** (관찰, 공개 문서에 없음)
  - Desktop 앱 안에 `start_session`이라는 내부 도구가 있다. 사용자가 그 턴에 직접 "세션 띄워"라고 말해야 하고, 그렇게 만든 세션은 다시 세션을 만들지 못한다. 문서에 없는 기능이라 기본 경로로 삼지 않는다.
- **에이전트 팀** (문서): 실험 기능이고 터미널에서만 된다. Desktop에서는 안 되고 재개하면 팀원이 복원되지 않는다. 쓰지 않는다.

## 2. 권한 — 10/2에 막혔던 것
- 막힌 것 둘: `docs/decisions.md`에 "사용자가 골랐다" 줄 쓰기, push 뒤 원격 확인 명령 묶음.
- 정식 해결 (문서, 시험 안 함): Song이 `~/.claude/settings.json`의 `permissions`에 좁은 규칙을 직접 넣는다. 평가 순서는 deny → ask → allow이고 이 규칙이 분류기보다 먼저다.
  - 경로 규칙은 `Edit(//절대/경로)` 형태, Bash 규칙은 `Bash(git push *)`처럼 뒤에 공백과 별표.
  - 넓은 push 허용은 강제 push까지 통과시키므로 deny를 함께 둔다.
- 분류기에 환경을 알려 주는 `autoMode` 설정은 사용자 설정에서만 읽힌다. 프로젝트 설정에 넣으면 무시된다.
- 대화로 말한 경계와 승인은 대화가 압축되면 사라질 수 있다. 오래 지킬 것은 규칙이나 파일로 둔다.
- 구체 규칙은 [Song이 넣을 설정](pm-drafts/settings-for-song.md)에 있다.

## 4. 동결 뒤 하나씩 시험해 붙일 것 (추천 순)
1. **실제 응답 모델 기록 훅** (문서): 작업자를 부른 뒤 실제로 어느 모델이 답했는지 기록한다. "다른 모델이 검토했다"의 근거가 된다.
2. **하위 에이전트 시작 훅** (문서): 정의 파일 없이 뜨는 하위 에이전트에게도 동결·2026 금지 규칙을 넣어 준다.
3. **편집 뒤 테스트 훅 고치기** (관찰 + 문서): 지금 훅은 편집할 때마다 `pytest tests -q -x`를 돌리고, 문서에 따르면 하위 에이전트 안에서도 실행된다.
4. **Playwright MCP** (문서, Microsoft 공식): 폰 크기 화면으로 열어 스크린샷과 화면 구조를 증거로 남긴다. 화면 작업자에게만 붙이고, 운영 서버가 아닌 시험 주소에만 쓴다.
5. **아침·저녁 브리핑 예약** (문서): Desktop 예약 작업은 이 맥이 켜져 있을 때 로컬 파일을 읽을 수 있다. 클라우드 예약(Routines)은 맥의 SSD 자료에 닿지 못해 맞지 않는다.
6. **PM 반복 절차를 스킬로** (문서): 아침 브리핑, 작업 배정, 검토 게이트, 결정 줄 초안, 저녁 브리핑. `.claude/skills/<이름>/SKILL.md`.
7. **저장 워크플로** (문서): push 전 점검이나 상태 훑기처럼 반복되는 여러 에이전트 작업.
8. **W&B MCP** (문서, 공식): 실험 지표 조회. 2026 평가 실행이 섞이지 않게 조회 범위를 먼저 정해야 한다.
9. **공식 플러그인** (문서): 폰용 상태 페이지(project-artifact), PR 검토 묶음(pr-review-toolkit). 설치 전에 컨텍스트 비용을 본다.

## 5. 쓰지 않는 것과 이유
- 에이전트 팀을 상시 구조로: 실험 기능, Desktop 불가.
- 클라우드 세션·Projects·Routines로 실험: 맥의 SSD 자료에 닿지 못하고, 레포가 공개 상태다.
- Linear·Jira·Notion을 작업판이나 결정 기록으로: "레포가 유일한 출처" 원칙과 부딪힌다.
- 권한 확인을 끄는 실행 방식(작업자 무인 실행 포함).
- `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`: 검토자까지 Opus가 돼 다른 모델 검토가 깨진다.
- 프로젝트 공용 설정에 PM 에이전트 고정: 그 레포의 모든 세션이 PM이 된다.
- 워크플로 상시 켜기(ultracode): 동시 실행 한도와 큰 워크플로 경고가 꺼지고, 모델을 적지 않은 에이전트가 Fable로 돈다.
- Sentry(계측 코드가 필요, 동결 중), MLflow(이 레포는 W&B), 참조용 메모리·파일·git MCP(기본 기능과 겹침), 커뮤니티 현황판 도구(출처 확인 못함).
